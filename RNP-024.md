# **RNP-024: Proposal for the Forth Growth & Adoption Incentive Program**

| RNP \# | Title | Category | Authors | Created | Status |
| ----- | ----- | ----- | ----- | ----- | ----- |
| 024 | Forth: AI Demand Routing, RENDER Payments and Usage Incentives | Network | Render Labs | 10-16-2026 | Draft |

## 

## **TL;DR**

This RNP proposes the launch and incentivization of **Forth**, a privacy-first AI gateway, routing, and payment layer that gives users, developers, applications, and autonomous agents a single API endpoint for accessing AI models and compute across multiple infrastructure types.

Through one interface, Forth can connect users to:

* privately hosted and user-controlled AI infrastructure;  
* anonymized third-party and frontier AI models;  
* Render Network and other distributed GPU compute;  
* future confidential-compute infrastructure; and  
* image, video, audio, inference, tool, and agentic AI services.

Forth handles authentication, privacy policy, model discovery and selection, infrastructure routing, metering, spending controls, payments, availability, and fallback routing behind the scenes. Users and applications may select a specific model or allow Forth to choose an appropriate model automatically.

Applications can integrate once and allow Forth to select the appropriate model or compute environment for a workload without requiring the application to integrate separately with every provider. This reflects the underlying Forth architecture, in which a standard AI endpoint sits between the user and multiple private, cloud, and distributed execution environments.

Privacy is a core part of the architecture. Sensitive workloads can remain on user- or organization-controlled hardware, cloud requests can be routed with user identity separated from the model provider, and payment identity is deliberately kept separate from encrypted conversation history. Future infrastructure may also support cryptographically verifiable confidential compute.

Forth is also intended to become a **demand aggregation layer for the Render ecosystem**. Rather than requiring every AI user or application to understand the underlying Render Network architecture, Forth can serve as a front door through which AI demand enters the ecosystem and, where technically and economically appropriate, is routed toward Render Network compute.

The Router is designed to support wallet-native payment through the x402 protocol on Solana using RENDER and USDC, alongside conventional card payment through MoonPay Commerce. This provides both crypto-native users and autonomous agents with programmatic payment capabilities while offering a familiar onboarding path for users who prefer to pay by card. Chat usage can draw against prepaid credit, while predictable-cost generation jobs can be paid for independently.

To accelerate adoption, this RNP authorizes a **time-limited, performance-gated incentive program of up to 500,000 RENDER**. The program is designed to reward economically meaningful activity rather than easily farmed product actions. In particular, it would:

* reward real paid Forth usage;  
* provide additional incentives for paying with RENDER;  
* provide additional incentives for workloads executed through eligible Render Network compute;  
* reward sustained usage and economically productive referrals;  
* exclude free credits, failed or refunded jobs, circular activity, and other non-economic or abusive behavior;  
* cap rewards relative to actual economic activity;  
* require public reporting on paid usage, RENDER payments, Render Network compute usage, incentive distributions, and BME-related activity; and  
* require any authorization beyond the 500,000 RENDER maximum to return through the RNP process.

The proposed incentives would be funded from existing Network growth and operations resources and would **not increase the existing RENDER emissions cap**. The long-term objective is not continued subsidization, but to establish Forth as a persistent source of AI demand, RENDER payment utility, Render Network workloads, and ultimately BME-related economic activity.

# **Overview**

Artificial intelligence usage is becoming increasingly fragmented.

Users today may interact with multiple frontier AI providers, open-source models, local GPUs, distributed inference networks, media generation services, coding models, and specialized agents. Each generally requires its own:

* API credentials;

* billing system;  
* model endpoint;  
* privacy assumptions;  
* pricing structure;  
* infrastructure configuration; and  
* integration.

Forth is designed to abstract this fragmentation behind a single interface.

A user or application points its AI client toward Forth rather than configuring each underlying provider separately.

Forth then manages:

> **User / Agent → Forth → Appropriate Model or Compute Provider**

The underlying system described in the current technical specification already supports a privacy gateway that routes requests between cloud services and user-controlled hardware while providing authentication, cost tracking, and automated model selection.

The architecture separates model access into privacy classes including private/local compute, anonymized cloud access, and burst capacity.

Forth can therefore serve two complementary purposes for the Render ecosystem:

1. **An AI product used directly by consumers, developers, and agents.**

2. **A demand aggregation layer capable of directing compatible workloads toward Render Network compute.**

This proposal is intended to accelerate both.

Forth will be built by OTOY, which will lead development and production implementation. The product will proceed through the production-readiness and launch stages described in the implementation plan below. Operational responsibility for the live service will be confirmed and publicly disclosed prior to launch.

---

### **Product and API Access**

Forth is intended to support both direct user interaction and developer integration. Users can access Forth through a user-facing interface for interacting with supported AI models and services, while developers, applications, and autonomous agents can access the same underlying routing layer through a standard API.

A developer can therefore integrate with Forth once rather than maintaining separate integrations with each underlying model or infrastructure provider. As supported providers, models, and compute environments change, the application can continue using the same Forth endpoint.

# **Reasoning**

## **The AI market needs a routing layer**

The number of useful AI models and infrastructure providers continues to expand.

Different models increasingly excel at different tasks:

* coding;

* reasoning;  
* creative writing;  
* image generation;  
* video;  
* speech;  
* research;  
* tool use;  
* agentic workflows;  
* local/private inference; and  
* specialized enterprise workloads.

It is increasingly inefficient for applications to integrate each provider independently.

Forth allows developers to integrate once and dynamically select the best infrastructure for a given job.

The long-term value of the Router is therefore not dependent on any individual model provider.

As models change, applications using Forth do not need to change their endpoint.

---

# **Why This Matters to the Render Network**

The Render Network has developed significant decentralized GPU infrastructure across rendering and general-purpose AI compute.

Previous RNPs have progressively expanded the Network's role beyond traditional rendering.

RNP-019 established a dedicated general and AI compute subnet and explicitly identified inference as one of the intended use cases.

RNP-022 subsequently maintained significant allocations for both AI-related grants and compute infrastructure as part of the Year 3 BME budget.

The challenge is not only creating GPU supply.

It is creating **easy-to-access demand**.

Forth is intended to become a front door through which AI demand can enter the Render ecosystem without requiring every user or application to understand the underlying Network architecture.

# **Forth Architecture**

Forth is designed as a standard AI API interface.

Existing tools and applications can change their AI endpoint to Forth and continue operating using familiar API patterns.

The Router manages:

* authentication;  
* model discovery;  
* metering;  
* spending limits;  
* routing;  
* privacy policy;  
* payment;  
* model availability; and  
* fallback infrastructure.

The technical specification describes the underlying routing architecture as capable of automatically selecting different models depending on the requested task while maintaining the selected model for subsequent conversation turns where appropriate.

Users and applications may also select a specific model where desired, or allow Forth to automatically select an appropriate model based on the requested task, availability, policy, and other routing considerations.

This architecture makes Forth particularly suited to:

* coding tools;  
* agent frameworks;  
* enterprise AI;  
* consumer chat interfaces;  
* AI-powered applications;  
* media generation;  
* autonomous purchasing agents; and  
* model experimentation.

---

# **Privacy**

Privacy is a core component of Forth.

The Router supports different classes of model access, enabling users to select between infrastructure that is:

### **Private**

Runs on hardware controlled by the user or organization.

Requests do not leave the private network.

### **Anonymous / Anonymized Cloud**

Requests may use external providers while user identity is separated from the model request.

### **Render / Distributed Compute**

Compatible workloads can increasingly be directed toward decentralized GPU capacity.

### **Future Confidential Compute**

Future infrastructure may support trusted execution environments or other cryptographically verifiable confidential compute.

The underlying architecture also deliberately separates payment identity from encrypted conversation history.

The payment wallet and the encrypted chat/history identity are not joined in the server-side data model.

**Reward calculations under this RNP shall not require analysis of prompt or conversation content.**

---

# **RENDER Payments**

Forth is designed to support accountless payment using the x402 protocol on Solana.

The current technical specification provides for payment using:

* **RENDER**; and

* **USDC**.

In addition to wallet-native payments, Forth is intended to support conventional card payments through MoonPay Commerce, providing a familiar payment path for users who do not wish to acquire or manage crypto assets directly.

A user or autonomous agent with a funded wallet can therefore purchase AI usage directly through x402 without requiring a conventional account or API-key issuance workflow, while users preferring conventional payment methods may fund their usage by card.

Chat usage is designed to draw against prepaid credit because per-message onchain settlement would be inefficient for very small transactions, while predictable-cost media-generation jobs may settle independently.

This is particularly useful for autonomous AI agents, which can programmatically purchase their own inference.

---

# **RENDER Payment Discount**

The Foundation intends to support a product-level discount for users choosing to fund Forth with RENDER rather than stablecoin or conventional payment rails.

The technical system already contemplates a configurable RENDER discount, with approximately **5%** used as an example implementation parameter.

This discount would be funded as a **Forth customer-acquisition expense** and would not be charged against the Foundation incentive allocation authorized by this RNP.

This creates immediate RENDER utility independent of the points program described below.

---

# **Proposed Forth Incentive Program**

This RNP authorizes a maximum of:

## **500,000 RENDER**

for a time-limited Forth growth incentive program.

The program will run for a maximum of **12 months following launch**, or until the authorized incentive allocation is exhausted, whichever occurs first.

The authorization is a maximum allocation.

It does **not** require the Foundation to distribute the entire 500,000 RENDER.

Rewards will only be distributed in response to qualifying economic activity.

---

# **Funding Source**

The proposed incentive allocation will come from existing Render Network Foundation resources available for:

* Network growth;

* R\&D;

* AI ecosystem development;  
* community growth initiatives; and/or  
* related customer-acquisition activity.

No additional emissions beyond the existing BME emissions cap are authorized by this proposal.

This approach follows the broader precedent of funding Network expansion from existing allocations rather than automatically increasing emissions.

RNP-023, for example, structures integration incentives from existing Network Operations treasury resources and makes incentives dependent on performance milestones.

---

# **Incentive Design**

The incentive system is designed around one central principle:

> **Reward economically meaningful behavior rather than easily farmed actions.**

Users will not earn Foundation-funded rewards merely for:

* creating an account;

* opening the application;  
* sending free requests;  
* connecting a wallet;  
* generating referrals that never become active; or  
* repeatedly triggering zero-cost events.

The principal scoring input is **real paid usage of Forth**.

---

# **Forth Points**

Users participating in the program will earn non-transferable **Forth Points**.

Points represent a user's relative contribution to qualifying Forth activity.

Points:

* are not transferable;

* do not represent RENDER;  
* have no guaranteed cash value;  
* cannot be sold;  
* may be adjusted for abuse or invalid activity; and  
* determine proportional participation in periodic RENDER reward pools.

The maximum RENDER allocation is disclosed through this proposal.

There is no guaranteed fixed points-to-RENDER conversion rate.

---

# **Qualifying Spend**

For purposes of incentive scoring:

**Net Eligible Spend** means externally funded, successfully consumed Forth services.

The following qualify:

* RENDER-funded inference;

* stablecoin-funded inference;  
* fiat-funded inference;  
* paid image or video generation;  
* paid AI tool usage;  
* paid agent/API usage; and  
* other paid Router services approved during the program.

The following do **not** qualify:

* free-tier usage;

* Foundation-funded promotional credits;  
* reward credits;  
* signup bonuses;  
* failed jobs that are refunded;  
* reversed payments;  
* chargebacks;  
* circular transactions;  
* Foundation testing;  
* employee/test accounts; or  
* activity determined to be fraudulent or primarily intended to farm incentives.

---

# **Scoring Formula**

Each user's monthly score will be calculated approximately as:

**Monthly Score \= Eligible Spend Score × Payment Multiplier × Route Multiplier × Retention Multiplier \+ Referral Score**

The Foundation may make minor parameter adjustments during the pilot where necessary for abuse prevention or product-market fit, provided that:

* changes are publicly disclosed;

* the maximum 500,000 RENDER authorization is not increased; and  
* changes do not retroactively remove legitimately earned rewards without cause.

---

# **Eligible Spend Score**

Only the first **\$1,000 equivalent of monthly net paid usage per reward principal** will receive the full spending-based incentive score.

Spending above the qualifying ceiling remains valid paid Router activity and contributes to Network usage metrics, but does not indefinitely increase a user's reward share.

This prevents the program from becoming primarily a subsidy to a small number of very large users.

The precise qualifying-spend ceiling may be reduced during the pilot if concentration becomes excessive.

---

# **Payment Multiplier**

Users paying for qualifying usage with RENDER receive an additional scoring benefit.

Proposed initial multiplier:

| Payment Method | Multiplier |
| ----- | ----- |
| RENDER | **1.10×** |
| USDC / fiat / other approved payment | **1.00×** |

This multiplier is intentionally modest.

The goal is to create an incentive to use RENDER without making payment-method selection more important than actual product usage.

---

# **Render Compute Multiplier**

Work executed using eligible Render Network compute receives an additional multiplier.

Proposed initial multiplier:

| Route | Multiplier |
| ----- | ----- |
| Eligible Render Network compute | **1.25×** |
| Other paid infrastructure | **1.00×** |

This is one of the most important components of the proposal.

The program should not merely subsidize consumption of third-party AI APIs.

It should increasingly incentivize users to consume AI workloads that create demand for the Render Network.

Where a workload cannot technically or economically execute on Render infrastructure, it remains eligible for the baseline program.

---

# **Retention Multiplier**

The program is intended to reward sustained adoption rather than one-time reward farming.

An initial retention schedule may be:

| Consecutive active paid usage | Multiplier |
| ----- | ----- |
| First active period | 1.00× |
| 4 consecutive active weeks | 1.10× |
| 8 consecutive active weeks | 1.20× |
| 12+ consecutive active weeks | 1.30× |

An active week requires a defined minimum amount of genuine paid usage.

A zero-value request or promotional-credit request cannot maintain a streak.

---

# **Maximum Combined Multiplier**

To prevent excessively leveraged scoring:

## **Payment × Route × Retention multipliers will be capped at 1.50×.**

This cap may be reduced if the incentive program becomes overly concentrated.

---

### **Referral Incentives**

Referrals can support productive Network growth, but they are also a potential source of Sybil abuse. Referral incentives are therefore divided between an ongoing Forth product-credit reward and a time-limited contribution to the Forth Points scoring system.

A referral becomes eligible once the referred user has completed:

> **\$20 of Net Eligible Spend on Forth using externally funded value, excluding promotional, referral, reward, or other platform-issued credits.**

Once this threshold is met:

* **Referral credit:** The referrer receives **\$20 in Forth credits**. This is a product-level referral incentive and continues on an ongoing basis, including after the referral-points period has ended. Referral credits themselves do not constitute Net Eligible Spend and do not generate points.  
* **Referral Score:** For the first 12 weeks following referral activation, the referrer receives an additional Referral Score based on the referred user’s qualifying activity:  
  * **Weeks 1–4:** 20% of the referred user’s eligible non-referral score.  
  * **Weeks 5–12:** 5% of the referred user’s eligible non-referral score.

For this purpose, the referred user’s **eligible non-referral score** means the score generated from their Eligible Spend Score and applicable Payment, Route, and Retention multipliers, excluding any Referral Score they may themselves have earned.

The resulting Referral Score is added to the referrer’s overall score under the program’s standard scoring formula and therefore contributes to the referrer’s proportional participation in the applicable RENDER reward pool. It does not represent a fixed amount of RENDER or a guaranteed points-to-RENDER conversion.

After the referred user’s 12-week referral-scoring period ends, the referrer no longer earns Referral Score from that referred user. The \$20 Forth referral-credit incentive continues independently, but referrals no longer generate additional points or increase participation in RENDER reward pools.

Self-referrals, circular referral structures, related-account farming, exploitative referral graphs, and other abusive or manipulative activity are ineligible for both referral credits and Referral Score.

---

# **Monthly RENDER Reward Pool**

Rewards will be distributed periodically from a fixed maximum authorization rather than being minted as an unlimited function of activity.

The maximum monthly distribution shall initially be:

## **50,000 RENDER per month**

subject to the cumulative 500,000 RENDER program cap.

However, the monthly pool is also limited by qualifying economic activity.

The RENDER distributed in a given reward period may not exceed a predetermined percentage of qualifying paid Forth usage.

The proposed initial maximum is:

## **20% of Net Eligible Spend, measured in USD equivalent.**

Therefore:

**Monthly Reward Pool \= lesser of:**

* 50,000 RENDER;

* remaining RNP incentive allocation; and  
* the RENDER equivalent of 20% of qualifying monthly paid usage.

This prevents large token distributions in periods where genuine product demand remains low.

---

# **User Distribution**

Each eligible user's RENDER allocation for a reward period is:

**User Reward \= Monthly Reward Pool × User Score / Total Eligible Scores**

Example:

If:

* the monthly pool is 10,000 RENDER; and

* a user earned 2% of all eligible points;

the user's provisional reward would be:

**200 RENDER**

subject to fraud review and applicable individual reward caps.

---

# **Individual Reward Guardrail**

The program should not enable a participant to spend a trivial amount and receive a disproportionately large RENDER payout.

The implementation will therefore include an individual economic cap.

At launch, a participant's reward value should generally not exceed **50% of the economically attributable qualifying spend associated with that participant and qualifying referrals during the relevant period.**

This parameter may be reduced as the program matures.

---

# **Reward Tranches**

To reduce treasury risk, the 500,000 RENDER authorization will be operationally divided into stages.

### **Phase 1 — Initial Pilot**

Maximum distribution:

**100,000 RENDER**

Requirements before launch:

* RENDER payment support operational;

* eligibility accounting operational;  
* refund/chargeback exclusion operational;  
* basic anti-Sybil controls operational; and  
* public reporting framework defined.

### **Phase 2 — Growth**

An additional:

**150,000 RENDER**

may become available once:

* the initial pilot has completed;

* meaningful paid activity has been demonstrated;  
* reporting is publicly available;  
* no material unresolved incentive exploit has been identified; and  
* Render Compute routing metrics can be independently reported.

### **Phase 3 — Scale**

The remaining:

**250,000 RENDER**

may become available following continued economic usage and satisfactory review of:

* customer acquisition;

* paid retention;  
* RENDER payment adoption;  
* Render Network workload generation;  
* incentive efficiency;  
* Sybil/fraud losses; and  
* BME integration progress.

The Foundation may decline to unlock subsequent phases.

---

# **BME Integration**

The long-term economic objective is for Forth to create recurring RENDER utility rather than rely indefinitely on incentives.

The technical specification explicitly anticipates a future integration in which revenue received through the Router can be connected to the Render Network's burn-and-mint economics.

This proposal establishes BME integration as a strategic objective of Forth.

### **Render Compute Workloads**

Where an AI workload executes on Render Network infrastructure, the relevant payment flow should use the canonical Render Network economic model applicable to that compute service.

### **Third-Party AI Workloads**

Where Forth purchases inference from a third-party model provider, the entire customer payment cannot necessarily be burned because the underlying model provider must be paid.

For those workloads, the Foundation will develop and publicly disclose an economically sustainable methodology for applying some portion of Router economics to RENDER utility and/or BME.

Potential mechanisms include:

* a percentage of Router platform revenue;

* a percentage of Router gross margin;  
* RENDER-denominated platform fees; or  
* periodic buy-and-burn funded from Router economics.

Any mechanism will be designed so that incentives do not require permanently subsidizing third-party model-provider costs.

---

# **Why Not Reward Every Request?**

Rewarding request count independently from spend would create undesirable incentives.

A user could:

* select extremely cheap models;

* generate unnecessary traffic;  
* automate low-value calls; and  
* farm rewards without generating equivalent economic value.

Forth will therefore emphasize actual economic consumption rather than raw request volume.

---

# **Why Use Points Instead of Paying RENDER Immediately?**

A points system provides several advantages.

### **Fixed Foundation Liability**

The RENDER pool remains capped.

### **Sybil Review**

Suspicious activity can be investigated before token distribution.

### **Relative Contribution**

Users compete for a fixed pool rather than generating unlimited token obligations.

### **Parameter Flexibility**

Scoring can be adjusted prospectively if unforeseen behavior appears.

### **Better Retention**

Periodic scoring encourages sustained usage rather than one-time extraction.

---

# **Anti-Sybil and Abuse Controls**

The incentive program creates a financial reward and should therefore assume adversarial behavior.

Forth and the Foundation may exclude activity based on indicators including:

* self-referrals;

* circular wallet activity;  
* repeated refund behavior;  
* chargeback patterns;  
* coordinated wallet clusters;  
* abnormal request patterns;  
* automated behavior whose primary purpose appears to be rewards farming;  
* exploitative referral graphs;  
* duplicate or controlled payment principals;  
* artificially generated traffic;  
* collusion between accounts; and  
* other objectively suspicious economic behavior.

Anti-Sybil analysis should primarily rely on payment and operational metadata.

**Prompt content and encrypted conversation history will not be used for points scoring.**

---

# **Refunds**

Refunded or failed paid usage does not generate incentive credit.

If a job receives a business-logic refund, its qualifying spend is removed from reward calculations.

The underlying Forth payment architecture already contemplates re-crediting failed jobs at the internal balance layer rather than reversing every payment onchain.

---

A public dashboard or periodic Foundation report should include, at minimum:

* Total paid Forth usage;

* Number of active paying principals;  
* RENDER-funded usage;  
* Percentage of payment volume denominated in RENDER;  
* Qualifying incentive spend;  
* RENDER distributed through the incentive program;  
* Average customer incentive rate;  
* 4-week and 8-week paid retention;  
* Referral-driven paid usage;  
* Render Network compute jobs routed through Forth;  
* Render Compute revenue attributable to Router usage;  
* Applicable RENDER burns;  
* Cumulative incentive allocation remaining; and

Reporting should be aggregate where disclosure of individual user information would undermine privacy.

# **Technical Considerations**

## **x402**

Forth's current technical specification uses the x402 HTTP payment protocol on Solana and contemplates both RENDER and USDC settlement.

## **Pricing**

Internal service pricing can remain denominated in USD while RENDER payment amounts are quoted at transaction time through an oracle.

The technical specification already describes converting USD pricing into RENDER amounts using a Solana-based RENDER/USD price feed with a configurable quote spread and quote expiration.

## **Wallets**

Forth can support standard Solana wallets without requiring custody of private keys.

## **Privacy**

Payment identity and encrypted history remain logically separated.

## **Metering**

Chat and token-based AI usage can be metered against prepaid credit.

Predictable media-generation calls can be priced per operation.

# **Foundation Authority**

During the program, the Render Network Foundation may:

* Lower monthly reward caps;

* Reduce multipliers;  
* Pause the incentive program;  
* Strengthen eligibility requirements;  
* Exclude compromised activity;  
* Modify anti-Sybil systems;  
* Adjust the qualifying-spend ceiling; and  
* Delay a reward period while fraud is investigated.

Material changes will be publicly communicated.

The Foundation may **not**:

* Increase the maximum allocation above 500,000 RENDER; or

* Extend the program beyond its authorized period

without further governance approval.

---

# **Program Sunset**

The program ends upon the earliest of:

1. 12 months after incentive launch;

2. Distribution of 500,000 RENDER;  
3. A Foundation determination that the incentives are economically ineffective; or  
4. A material technical, legal, security, or abuse issue requiring termination.

Unused RENDER remains with the applicable Foundation treasury.

Continuation would require further governance authorization.

# **Potential Drawbacks**

## **Incentive Farming**

Any token reward program attracts economically motivated abuse.

This is mitigated through spend gating, refund exclusion, referral requirements, proportional reward pools, individual caps, and retrospective fraud review.

## **Subsidized Demand May Not Persist**

Some users may stop using Forth when incentives end.

For this reason, retention and post-incentive behavior should be measured continuously.

## **Third-Party Model Spend Does Not Automatically Benefit Render Compute**

Early Forth activity may use centralized model providers.

This is why Render Network-routed workloads receive higher scoring and why the long-term plan emphasizes Render Compute routing.

## **Treasury Cost**

The Foundation may distribute up to 500,000 RENDER.

This cost should be compared with:

* Paid usage created;

* User retention;  
* Render Compute revenue;  
* RENDER payment adoption;  
* BME activity; and  
* Customer-acquisition cost.

## **Token Price Volatility**

The USD value of a fixed RENDER pool can fluctuate substantially.

Monthly activity-based caps reduce the risk of incentives becoming disproportionate to customer spending.

## **Privacy / Fraud Tradeoff**

Strong fraud prevention can conflict with privacy if implemented poorly.

The program should therefore rely on economic and operational signals wherever possible and should not inspect private prompt contents for reward eligibility.

---

# **Economic Rationale**

The objective of the program is not simply to distribute RENDER.

The intended cycle is:

**RENDER incentives**

→ **New Forth users**

→ **Paid AI usage**

→ **Greater RENDER payment utility**

→ **Greater AI demand aggregation**

→ **Greater Render Network compute demand**

→ **BME activity**

→ **Less dependence on incentives**

The ideal outcome is that the program becomes unnecessary because Forth itself produces recurring demand and economic activity for the Network.

---

# **Success Metrics**

The program should be considered successful if it creates meaningful improvement in several of the following metrics:

* Cumulative paid Forth spend;

* Paying-user growth;  
* Paying-user retention;  
* Percentage of customers funding accounts with RENDER;  
* Frequency of repeat top-ups;  
* Referral conversion to paid usage;  
* Percentage of compatible work routed through Render Compute;  
* Revenue generated for Render Network nodes;  
* RENDER burned through Router-related activity;  
* Incentive cost as a percentage of paid usage; and  
* Organic usage following reduction or removal of rewards.

The primary success metric should **not** be points issued or accounts created.

It should be economically productive usage.

# **Relationship to Prior RNPs**

This proposal builds upon several previously approved directions in the Render ecosystem.

RNP-006 established a precedent for substantial **points-based incentives**, allocating up to approximately 1.14M RENDER-equivalent tokens to points incentives in its Year 1 emissions design.

RNP-013 explicitly identified artist rewards as usable for rebates, ambassadors, customer acquisition, and referral programs intended to bring additional paying users onto the Network.

RNP-019 established the Render Compute Network for AI and general-purpose compute workloads.

RNP-022 maintains substantial Year 3 allocations for AI grants, node rewards, operations, R\&D, and growth initiatives.

RNP-023 provides a recent model for Network expansion in which incentives are funded from existing treasury resources and are tied to time and performance milestones rather than being distributed unconditionally.

This RNP applies those principles to a demand-side AI product.

# **Conclusion**

The Render Network has spent several years expanding GPU supply, compute capabilities, payment infrastructure, and BME economics.

Forth is intended to build a complementary layer:

**demand aggregation.**

Instead of requiring users to learn how individual GPU networks, AI providers, wallets, billing systems, privacy systems, and model APIs operate, Forth provides a unified entry point.

The proposed incentive program uses a capped amount of RENDER to accelerate adoption while deliberately tying rewards to behaviors that generate economic value:

* Paying for AI;

* Paying with RENDER;  
* Returning over time;  
* Referring real paying users; and  
* Consuming Render Network compute.

The proposal authorizes no increase to the existing emissions cap.

It places a maximum limit on Foundation exposure, ties distributions to actual paid activity, requires public reporting, and gives the Foundation the ability to pause or reduce incentives if the economics do not work.

If successful, Forth can evolve from an incentivized customer-acquisition program into a persistent source of AI demand, RENDER utility, Render Compute workloads, and BME activity for the Network.
